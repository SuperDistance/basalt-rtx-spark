# What changed for RTX Spark?

Upstream Basalt supplied Flash-Next inference, its expert cache, speculative decoding and chunked prefill. The original Arm64 port added native Windows Arm64 and CUDA `sm_121` support. This fork builds on both to shorten the wait for a first token and keep other chats responsive on a laptop with shared CPU and GPU memory. [Upstream fork point](https://github.com/jesdga95/basalt/tree/63cb68ad471a443811ae171da0395bc3f1fc3ab5) · [Arm64 port used for benchmarks](https://github.com/yanmindi/basalt-arm-sm121/tree/2ec7a844f9d83cda0fa579801f85cd8898a12bec) · [RTX Spark release source](https://github.com/SuperDistance/basalt-rtx-spark/tree/bd05fdf80da36d52f7e7b1978d635243c7aff6cc)

| What the fork adds | What it does on N1X |
| --- | --- |
| Read short FP4 prompts with BF16 activations | For NVFP4 chunks below 1,024 tokens, the integrated GPU widens the expert weights in registers and runs the products on BF16 tensor cores. A cold 716-token FP4-Local prompt reached its first token in **0.66 s**, down from **1.37 s** on the previous quantized matrix kernel. Across 100 chunks, mean divergence from the BF16 reference was 0.08847 versus 0.08877. [Kernel and quality measurements](n1x-gpu-first.md#nvfp4-prompts-on-bf16-activations-w4a16) |
| Reuse dense weights across prompt chunks | When GPU memory can hold the full-context KV reserve and dequantized weights, the engine keeps 300 FP16 projection matrices resident. The same matrix products can then run without unpacking the weights again. A roughly 110-token prompt took **158–176 ms** to read, down from **194–215 ms** in alternating runs. [Prompt measurements](n1x-prompt-path.md#the-dense-projections-copies) · [Matrix products](../src/models/qwen4exp/prefill/gemm.cu) |
| Draft several replies in one GPU pass | Flash-Next batches each draft step across active requests. A four-stream scheduler uses the time spent verifying proposals and the number of tokens kept to choose the next window. With four simultaneous 1,024-token structured replies, the release spent **5.42 ms per window drafting**, versus **21.53 ms** on the port. The scheduler alone raised throughput **8.1%** in a separate four-run comparison. [Release and port measurements](../benchmarks/results/2026-11-24-n1x-cooled-release#serving-behavior-under-load) · [Scheduler experiment](../benchmarks/results/2026-11-24-n1x-four-stream-scheduler#scheduler-alone) |
| Admit cold prompts while other replies stream | With active decodes, the fork lowers the threshold for overlapping a cold read from 16,384 to 2,048 tokens and spaces decode windows to give the incoming prompt GPU time. During a 16,672-token fourth request, the three existing chats each delivered **211–252 tokens** before its first token arrived at **26.17 s**. The longest gap between incumbent tokens was **389 ms**. [Serving code](../src/models/qwen4exp/serve/prompt_read.cpp) · [Request trace and power](../benchmarks/results/2026-11-24-n1x-cooled-release/release/cold-join.json) |
| Place experts across shared memory | The planner sizes GPU experts and their host backing together, taking account of physical RAM and how far the Windows page file can grow. The integrated GPU can read pinned host experts in place. On the 96 GiB GPU split the release placed **all 24,576 experts on the GPU** and configured **four 262,144-token slots** with INT8 KV allocated on demand. [Placement design](n1x-gpu-first.md) · [Measured configuration](../benchmarks/results/2026-11-24-n1x-cooled-release/release/run-config.json) |

In the complete BetterBench workload, the release read the nominal 2K cold prompts at **1,767 input tok/s**, versus **967** on the original port (**+82.7%**). Median first-token latency fell from **1.590 s to 0.878 s**. Each engine saw eight cold requests in this bucket, with a median of approximately 1,550 model tokens. Both used IQ3 weights and the same physical cooling setup. Busy GPU draw averaged **50.9 W** for the release and **48.4 W** for the port in this bucket. These sequential runs measure the combined engine changes.
